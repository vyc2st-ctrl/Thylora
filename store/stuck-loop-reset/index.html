What a stuck loop is

A stuck loop is not a hard problem. A hard problem moves when you push it. A stuck loop is the same attempt, repeated, with the same result, by someone who has run out of other ideas and is now hoping that effort will substitute for information.

How to tell you are in one

  • You have tried the same thing three or more times and the result did not change.
  • Your next idea is "try it again, but properly this time".
  • You cannot say which step last worked — only that the whole thing does not.
  • You have already spent longer on it than the task was ever worth.
  • Somebody could help, and you have not asked, because asking feels like losing.
RouteTwo of those five is enough. Stop attempting and run the six blocks. Repeating an attempt is not progress just because it is tiring.

The six blocks, in order

#BlockWhat it is for
1Stop duplicate attempts Stops the damage. A repeated attempt can charge twice, send twice, or overwrite the one good copy you still have.
2Preserve current state Keeps what already works. Most of the loss in a stuck loop happens after the problem, while trying to fix it.
3Last verified step Finds the floor. Not where you think it broke — the last point you actually saw working with your own eyes.
4One next action One. Not a list. A list is how a stuck loop hides as a plan.
5Escalation Gets a real answer instead of "any update?". There is a message on page 5 you can copy.
6Result record Makes this the last time. A loop that is never written down is a loop somebody runs again in six weeks.

The rule that makes the rest work: never restart from zero what is already partly done. Resume at the first gap. Everything before block 4 exists to find where that gap actually is.

THYLORA · STUCK LOOP RESET Blocks 1–3
01

Stop duplicate attempts

Put the attempt down. Then find out whether the earlier attempts left anything behind.

Ask Did any previous attempt half-succeed? Is anything queued, pending, submitted, charged, or sent that I cannot see from here?

Do Check before you retry, not after. A fifth attempt on a payment, an order, an email or an upload can double it. Where you cannot check, assume it went through and say so in block 5.

RouteIf a retry could charge, send or overwrite anything, you are not allowed another attempt until block 5 has been sent.
02

Preserve current state

Before anything else changes, keep a copy of what exists right now.

Ask If the next attempt makes this worse, what do I wish I had kept?

Do Copy the file, screenshot the screen, note the reference number, save the error text word for word, write down the time. Put it somewhere that is not the thing that is broken.

RouteTwo minutes here is the difference between a bad afternoon and a lost week. Do it even when you are sure it is not needed — especially then.
03

Last verified step

Find the last point you personally saw working. Verified means seen, not assumed.

Ask What is the last thing I watched succeed, with my own eyes, today?

Do Write it with a time against it. "The file opened at 10:40" is a verified step. "The upload was fine" is not.

RouteEverything between the last verified step and the failure is the only ground worth searching. Anything before it is already proved and does not need redoing — that is how you stop restarting from zero.

If you cannot name a verified step at all, that is the finding. Your next action is not to fix the problem — it is to get one thing working that you can see, however small, and build from there.

04

One next action

One action. Small enough to finish in twenty minutes, and specific enough that somebody else could do it exactly as written.

Ask What single thing, done next, would tell me something I do not already know?

Test it If it starts with "look into", "investigate" or "sort out", it is not an action. If it has an "and" in it, it is two.

RouteAn action that only repeats an earlier attempt is disqualified. The purpose of the next action is information, not effort.
05

Escalation

Escalation is not complaining and it is not giving up. It is handing someone the smallest piece of information that lets them answer.

Escalate when the next action needs an authority, an access or a fact you do not have — or when a retry could cost money and you cannot check.

Escalate to the person who can decide, named. Not a queue, not a group, not "the team".

RouteUse the message on page 5. It is built so the person reading it can answer with one word, not with a meeting.
06

Result record

Four lines, written once it is over, while you still remember.

Write what was actually wrong · what fixed it · what you would check first next time · whether anything is still held.

Keep it where the work lives, not in your own notes. The person who hits this next is not necessarily you.

RouteIf the loop ended because somebody else fixed it and you never learned how, write that down too. An unexplained fix is a loop waiting to return.

The honest exit: blocks 1–3 done, no next action available, escalation sent. That is a finished reset, not a failure. You are waiting on a named person for a named thing — which is a completely different state from being stuck.

The escalation message

Copy it, fill the five gaps, send it. It is short on purpose: a message that takes ten minutes to read gets answered tomorrow.

Subject: [what it is] — stuck after [n] attempts, need one decision

I have stopped attempting so I do not duplicate anything.

What I am trying to do: [one line]
Last thing I saw working: [step] at [time]
What happens instead: [exact error or behaviour, word for word]
Tried: [attempt 1], [attempt 2], [attempt 3] — same result each time
State preserved: [what you saved, and where]
Possible duplicate: [anything that may have half-gone-through, or "none found"]

What I need from you: [one specific thing — a yes/no, an access, a number, a decision]
If I hear nothing by [time], I will: [your default action]

[your name]

Why each line is there

  • Stopped attempting — tells them nothing is getting worse while they read.
  • Last thing working — hands them the search area instead of the whole system.
  • Word for word — a paraphrased error costs a round trip every time.
  • Tried — stops the first reply being something you already did.
  • Possible duplicate — the line that prevents a double charge or a double send.
  • One specific thing — makes a one-word answer possible.
  • If I hear nothing — a default, not a threat. It keeps the work moving and it makes silence a decision rather than a delay.

What to leave out

  • How long you have been on it. It is not evidence, and it invites a judgement about you instead of an answer about the problem.
  • Apologies. One is fine; three change the subject to your feelings.
  • Your theory of what is wrong, above the facts. Put it at the bottom, marked as a guess, or leave it out.
  • Anyone copied in who cannot decide anything. An audience slows an answer down.
RouteNo reply by your stated time? Send the same message once more with the new time, to the same person, and name who you will ask next.

Worked example

A fictional four-person distributor, Marrow & Fen Supply. The weekly stock list has to reach their largest customer by Tuesday noon. It has failed to send four times. It is 11:10.

#BlockWhat was written
1Stop duplicate attempts Stopped. Checked the sent folder: attempts two and three left nothing, but attempt four shows a partial upload sitting in the customer portal, timestamped 10:52 and marked INCOMPLETE. A fifth attempt might have created a second order.
2Preserve current state Saved the stock file as stock-11nov-BEFORE.csv on the desk machine, not in the shared folder. Screenshot of the portal error. Error text copied exactly: "Row 412: quantity field empty — upload halted".
3Last verified step The file opened correctly and showed all 508 rows at 10:31. The upload reached row 411 before halting. Everything up to row 411 is proved; only rows 412 onward are unknown ground.
4One next action Open row 412 and look at the quantity field. (Not "fix the file" — that is four actions wearing one coat.)
5Escalation Sent to the customer's named receiving clerk, not the general inbox: one question — "Does the incomplete upload from 10:52 need deleting before I resend, yes or no? If I hear nothing by 11:40 I will resend and flag it as a possible duplicate."
6Result record Row 412 had a quantity of "—" typed by hand instead of 0. The upload rejects non-numbers and names the row. Next time: check the row the error names before anything else — the message was accurate the first time and was read as generic. Still held: whether the portal keeps rejecting hand-typed dashes, asked of the clerk.

What the reset was worth

Eleven minutes, of which six were writing. It caught a half-finished upload that a fifth attempt would have duplicated into a second order, it found the fault in one row rather than 508, and it turned "it keeps failing" into a question a clerk answered in one word. Nothing in this example is real: Marrow & Fen Supply does not exist.

Provenance

The six blocks come from two rules proved inside THYLORA production: that a handoff with no record is where work disappears, and that an interrupted process should resume at the first gap rather than restart from zero. Block 3 is that second rule written for a person instead of a system.

Nothing in the worked example is real. Marrow & Fen Supply does not exist, and no customer, clerk or order in it refers to anyone.
